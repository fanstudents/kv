知識庫導入・AGENT 的底層核心

Agent 真正的核心，
不是模型，是你的知識庫。

同一個模型，餵不同的知識庫，就是完全不同的兩位員工。模型決定它「會不會講話」， 知識庫決定它「講不講得出你公司的事」——以及，講不講得出不該講的事。

L1–L4 四級資料分級 分級守在資料庫層 AI 產出一律先當草稿 每條都能回溯來源頁碼 誰引用了哪一條，查得到

為什麼知識庫是地基

沒有知識庫的 Agent，
只是一個很會講話的陌生人。

它讀過整個網際網路，卻沒讀過你的報價單。問它產業常識答得頭頭是道， 問它「這個客戶上次談到哪」就開始編。差別不在模型有多強，在它手上有沒有你的資料。

只有模型
通用的聰明，你的場景用不上

它會寫文案、會分析、會摘要——但它不知道你的退換貨政策寫什麼、 不知道哪個方案含哪些服務、不知道這位客戶簽的是哪一版合約。 問到公司內部的事，它有兩種反應：說不知道，或是編一個聽起來很合理的答案。 後者比前者危險得多。

Agent ＝ 模型
→ 一個很會講話的陌生人
模型 ＋ 知識庫 ＋ 權限
你的場景，加上該有的界線

接上知識庫之後，它回答的每一句都來自你審過的內容，還能標出處在第幾頁。 再加上分級權限，客服 Agent 讀得到 FAQ 與 SOP，但讀不到財務數字與客戶名單—— 不是「我們叫它不要說」，是它從資料庫撈不到那些資料。

Agent ＝ 模型 ＋ 你的知識庫 ＋ 讀取權限 ＋ 流程
→ 一位知道公司規矩的同事
SAME MODEL

一份知識庫，全隊共用

客服、業務、營運不是各自維護一份文件。同一個知識庫，依各自的等級讀到各自該讀的那一段。

GROUNDED

答案有出處，不是憑印象

匯入時每一條都記住來自哪一份文件的第幾頁，Agent 回答時可以附上出處，你查得到。

RETRIEVAL

只取跟問題相關的幾段

不是把整個知識庫塞給模型。用向量檢索挑出最相關的內容，答得更準，AI 成本也不會爆。

LIVING

會過期，就要能更新

價格改了、SOP 換了，知識庫要跟著改版。舊的封存但留著可追溯，不是直接刪掉當作沒發生。

為什麼不能「把檔案丟進去就好」

從一份 PDF 到能被問的知識，
中間有八關。

市面上的工具通常做到第三關就交給你了。剩下五關——尤其是敏感度判斷跟人審—— 是最花時間、最需要有人懂你的業務，也是最不能省的部分。

01
盤點與取得我們＋你

先搞清楚你手上有什麼：SOP、教育訓練、報價單、官網、產品型錄、客服對話紀錄。 支援上傳 PDF，也支援直接給網址，由系統抓成乾淨正文。

這一關的產出不是檔案，是一份「哪些能用、哪些不能碰」的清單。

02
抽取文字，保留頁碼系統

逐頁抽出內容而不是整份揉成一團——因為第 12 頁的那句話，日後要查得回去。

03
切塊系統

切太長 AI 會漏讀，切太短會失去上下文。切塊的顆粒度直接決定日後答得準不準。

04
轉成能被問的條目AI

這裡是關鍵：不是所有內容都適合寫成問答。流程要留成步驟、規格要留成表格、 數字要留成事實。硬把 SOP 壓成一問一答，Agent 就會漏掉中間的步驟。

條目型別：問答 / 步驟 / 事實 / 表格 / 文件——依內容性質選，不是一律轉成 FAQ。

05
敏感度預判AI

每一條先預判該落在 L1–L4 哪一級，並附上理由（例如「含金額」「含人名與聯絡方式」）。 這只是預判，不是定案——真正拍板的是下一關的人。

06
人審人・不可略過

AI 轉出來的東西一律是草稿。沒有人按過「通過」，就不會進任何一位 Agent 的腦袋。 這是把「AI 會編」擋在知識庫外面唯一有效的一關——也是為什麼這件事需要有人真的坐下來看。

審的不只是「對不對」，還有「這條該給誰看」。一條報價資訊被誤標成 L1， 就等於允許客服 Agent 對外講出你的成本結構。錯放一級，就是一次外洩。

07
發布並指派讀取權限人

每位 Agent 被指派一個「可讀取上限等級」。設定完成後，這條知識才真正開始工作。

08
維運：改版、封存、回頭看誰在用我們＋你

知識庫不是一次性專案。價格會改、政策會換、有些條目根本沒人用過。 系統會記錄每次回答引用了哪幾條，你才知道哪份知識真的在幫忙、哪份可以退場。

沒有更新與退場機制的知識庫，會隨著時間慢慢中毒——舊價格、舊政策繼續被當成正確答案講出去。

高資安知識庫怎麼做到

分級不是貼標籤，
是真的擋得住。

很多系統的「權限分級」只是 UI 上的一個欄位——實際撈資料時照樣全部撈出來， 再交代模型「這個不要講」。那不叫權限，那叫請求。我們把這道牆放在資料庫。

官網、型錄、FAQ、公開簡報

L2 以上

分級守在資料庫層，不是靠提示詞

檢索知識庫的函式本身就帶「這位 Agent 的上限等級」這個參數， 超過等級的內容在資料庫那一層就被濾掉，根本不會離開資料庫、 更不會出現在送給模型的內容裡。

match_kb_chunks(question, max_level: 2)
  → L1 ✓  L2 ✓  L3 ✗  L4 ✗
// L3/L4 的內容連撈都撈不出來

資料庫預設拒絕，只有伺服器進得去

知識庫資料表對匿名角色完全關閉，只有跑在伺服器端的服務金鑰能存取。 瀏覽器端沒有任何一把鑰匙——即使前端程式碼被完整看光，也拿不到讀取知識庫的權限。

  • 匿名與一般登入角色的資料表權限已收掉
  • 金鑰只存在伺服器環境變數，不進前端打包
  • 另可選擇自建部署，資料庫直接落在你自己的環境
DRAFT FIRST

沒人審過就進不了 prompt

AI 產出的條目狀態一律是「待審」。草稿不會被檢索、不會進任何 Agent 的回答。

TRACEABLE

每條都知道從哪來

來源文件、頁碼、版本號、負責人、下次複審日期都跟著條目走，不是一團無主的文字。

AUDIT

誰引用了哪一條，有紀錄

每次回答用到哪幾條知識都會留下引用紀錄，事後查得出這句話是根據哪份文件講的。

LIFECYCLE

退場不等於刪除

過期內容封存後就不再被檢索，但紀錄留著——之後要追「當時為什麼這樣答」還查得到。

導入服務範圍

工具給你，你還是得自己判斷；
我們做的是判斷的那部分。

上傳、切塊、轉條目這些，系統都做得到。真正花時間的是「這份能不能進」「該給誰看」 「這樣切對不對」——這些沒有辦法外包給 AI，只能有人陪你走一次。

知識庫盤點

陪你把散在雲端硬碟、LINE 群組、老員工腦袋裡的東西盤出來， 分成「馬上能用」「要整理才能用」「先不要碰」三堆。這一關通常會挖出比你預期更多的東西。

分級與權限設計

依你的產業與內部規範，把資料對到 L1–L4，再決定每位 Agent 的可讀取上限。 有法規要求（個資、醫療、金融）的話，這一關會做得更保守。

首批人審陪跑

第一批條目我們陪你一起審，順便把審查標準訂出來—— 之後你的同事接手時，有一份「什麼該過、什麼該退」的實際範例可以照著做。

來源串接與定期重爬

官網、產品頁這類會變動的來源，設定成定期重新抓取，改版了知識庫跟著更新， 不用有人記得手動同步。

答不準的回頭調校

上線後一定會有答不好的狀況。看引用紀錄就知道是「沒有這份知識」還是 「有但沒被檢索到」——兩種問題的解法完全不同，別瞎調。

交接給你的內部負責人

目標不是讓你長期依賴我們。流程順了之後，知識庫的日常維護交回你公司內部， 我們留在後面支援。

常被問到的問題

關於知識庫，
最常見的五個誤解。

我把所有檔案丟進去，AI 自己會整理吧？

會整理，但不會判斷。AI 能把一份 PDF 轉成一堆條目，卻分不出「這個報價是給 A 客戶的特案」 還是「這是公開定價」。前者被誤標成公開資料，客服 Agent 就會拿去回答下一個客人。 分級這件事，需要懂你業務的人拍板。

用市面上的 AI 工具上傳檔案，跟這個有什麼不同？

差別在三件事：一是分級——多數工具是全有或全無，沒有「這位員工只能讀到這一層」的概念； 二是人審——AI 轉出來的內容直接生效，沒有草稿這一關； 三是可追溯——答錯了查不出是根據哪份文件講的。日常問答夠用，但要放公司的合約、客戶名單， 這三件事缺一不可。

我們的資料很敏感，可以完全不出公司嗎？

可以。系統支援自建部署——資料庫、知識庫、對話紀錄全部落在你指定的環境（地端主機、NAS 或你自己的雲端帳號），不經過我們的伺服器存放。這種情況下，L4 這類最敏感的內容 通常會搭配內部部署的模型，或乾脆不進知識庫、只由人處理。詳細的兩種交付模式， 在介紹頁的資安段落有完整說明。

導入要多久？我們要投入多少人力？

取決於你的資料量與整理程度。實務上最花時間的不是系統，是人審—— 第一批條目通常需要你這邊指派一位熟悉業務的同事，跟我們一起看過。 我們的做法是先做一個範圍小、但完整走完八關的批次，讓你看到實際效果與投入程度， 再決定要不要擴大。

知識庫建好之後就不用管了嗎？

不是。價格、政策、產品都會變，知識庫沒跟著改，Agent 就會拿舊資訊回答—— 而且它講得跟真的一樣，沒人會發現。所以系統保留了版本、複審日期與引用紀錄， 就是為了讓「該更新什麼」變成看得見的事，而不是等客訴才發現。
